# ADR: Adaptive runtime as a resource economy, sensed by an Expo module

## 1. Context

The governor spec (2026-10-19) defines a facade with `sense`, `admit`,
`visualBudget` and telemetry, and names a Nitro module for native sensing.
The ledgers of 2026-10-19 and 2026-10-20 add five constraints this ADR keeps:
composition over a monolith, intrinsic efficiency before adaptive efficiency,
deterministic and versioned policies, the scroll-freeze rule, and the numeric
targets (cold start under 2.0 s on mid-tier Android, input under 100 ms,
resident memory under 180 MB).

Three facts the spec did not address:

1. **Capacity is temporal.** The same phone gives different capacity as it
   heats, drains and competes with other apps. A device tier is a prior, not a
   verdict.
2. **The users' phones sit low.** In Sri Lanka in September 2026 about 42% of
   Android web traffic ran on Android 13 or older and about 15% on 10 or older
   (StatCounter). The app's minimum is Android 9 (minSdk 28).
3. **Android signals differ by version.** Thermal status arrives at API 29,
   headroom and exit reasons at 30, frame deadlines and performance class at
   31 (checked against `api-versions.xml`, platform 35). From API 34 the system
   stops sending in-use memory trims.

The full design, feasibility and plan are in the Gurudevi Adaptive Runtime
document (Claude Docs, 2026-10-21); this ADR records the decisions.

## 2. Decisions

### D1. The runtime is a resource economy over three time layers

Seven accounts (cpu, gpu, memory, energy, thermal, network, storage). Supply is
read in three layers: baseline (what the device is), varying (what it can give
now) and realtime (what the app is spending). Demand is a registry of
workloads, each with a class, a quality ladder and a cost vector. An allocator
divides each account's budget among workloads in class order; the existing
governor (`packages/core/src/governor/`) is kept as its correction loop.

### D2. Four classes, mapped to the existing vocabulary

| Class | Spec `WorkCategory` | Glass priority | Shed |
| --- | --- | --- | --- |
| critical | `user-critical` | `critical` | never; degrades only inside its ladder |
| committed | `ui-transition` | `high`, `normal` | lowered, never removed |
| deferrable | `background-sync`, `media-prefetch`, `storage-cleanup`, `telemetry-flush` | none | postponed |
| ornamental | none | `low`, `decorative` | first |

The existing `admitWork` matrix and `VisualBudget` tiers remain the public
contract; they become views computed from the allocator's levels.

### D3. Native sensing is a Kotlin Expo module, not Nitro

`apps/gurudevi-mobile/modules/runtime-sense` measures and never decides.

- Decisions run on 500 ms windows and on state changes, so synchronous JSI
  access buys nothing. The cost that matters is how often anything crosses,
  and the module sends events only on change (an idle screen sends none).
- The Expo Modules API autolinks under CNG with no C++ toolchain, which fits
  the repo rule on native code and keeps it off the Tier 1 Nitro pin.
- The spec's figure of 70 to 120 ms per Expo call is not used here: it is not
  sourced in the audit and describes call volume, which this design avoids.
- If a later phase needs per-frame synchronous access from a worklet, Nitro
  can be added for that one path without changing the policy layer.

The frame estimator is held to golden vectors generated by the TypeScript
reference, so both implementations produce the same windows.

### D4. Every signal has a fallback to Android 9

Polling of free memory and the low-memory flag covers API 34 and later, where
trims are withheld. Battery temperature and frame-cost drift infer heat where
thermal status is absent (API 28). Each estimate carries a confidence, and
low confidence widens the allocator's safety margin.

### D5. Invariants

1. Critical work is admitted first; its budget is reserved.
2. No workload is lowered for an account it does not spend.
3. Every change records account, signal, value, rule and policy version.
4. Raising is slower than lowering; a failed raise doubles the wait.
5. Without signals the baseline holds; nothing guesses upward.
6. Native measures, TypeScript decides; every threshold has one source.
7. No quality change during a gesture or list momentum.
8. Policies are deterministic and versioned; telemetry informs the next
   version, never the running one.
9. A workload enters the allocator only after its intrinsic cost is checked.

### D6. Evidence before closed loop

Five modes: off, static, shadow, closed loop, minimal. Assignment is the
existing deterministic hash; a remote kill switch sends everyone to off. Closed
loop reaches users only after shadow data from real phones, with a primary
outcome named in advance and guardrails (crashes, ANRs, low-memory kills,
heat, energy) that must not worsen.

### D7. Every phase passes five gates

Waste, hardware, scaling, telemetry and independent critique, as defined in
the design document. A gate that cannot be met is recorded as an open risk.

### D8. Pilot freeze

Until after the teacher pilot on 2026-10-26, only TypeScript changes behind
flags that default to current behaviour may merge. `runtime-sense` stays on
`feat/adaptive-runtime`.

### D9. A lieutenant to the OS, and a veteran of each phone

The runtime is a supervisor for this app only, subordinate to the Android
kernel: it never fights the scheduler or the memory killer, it acts before the
OS has to act bluntly (kill, uniform throttle, ANR), and it reports every
decision. It learns each phone as it is now, because system updates and vendor
policy change capacity after sale: after an OTA, apps run with only the
`verify` compiler filter until the daily idle-and-charging background dexopt
(AOSP ART Service configuration), and in 2022 Samsung's Game Optimizing Service
throttled apps by identity (XDA Developers, 2022-03-04). A per-device profile
keyed by the build fingerprint records frame, thermal, memory and per-thread
baselines; a new fingerprint marks it stale. Learned values move thresholds
only within bounds fixed by the policy version, so policies stay deterministic
while facts about the phone are learned. First panel: the Galaxy A52 and
Galaxy A24 and friends' phones, in shadow and active mode, before and after
their next update.

## 3. Consequences

- The facade in the spec keeps its names; its internals change.
- A registry test will fail when a component animates, decodes, fetches or
  schedules without declaring a workload.
- Telemetry gains a policy version and reason on every decision, and a daily
  byte budget per device.
- Thresholds tuned on the Galaxy A52 are provisional until checked on a 2 to
  4 GB phone or constrained emulators.

## 4. Alternatives considered

| Alternative | Rejected because |
| --- | --- |
| Nitro module for sensing (the spec) | synchronous access is not needed at window granularity; adds C++ build risk on a Tier 1 pin |
| Visual-only adaptation (as in `expo-adaptive-glass`) | most of Gurudevi's cost is sync, storage, images and the JS thread |
| Fixed device tiers | the same device varies more within a session than tiers differ |
| Self-tuning policies | non-deterministic, unreproducible; rejected by the telemetry ledger |
| A C++ estimator shared across platforms | iOS is out of scope; golden vectors give parity without it |
