# ADR: Adaptive runtime as a resource economy, sensed by an Expo module

## 1. Context

The governor spec (2026-10-19) defines a facade with `sense`, `admit`,
`visualBudget` and telemetry, and names a Nitro module for native sensing.
The ledgers of 2026-10-19 and 2026-10-20 add five constraints this ADR keeps:
composition over a monolith, intrinsic efficiency before adaptive efficiency,
deterministic and versioned policies, the scroll-freeze rule, and the numeric
targets (cold start under 2.0 s on mid-tier Android, input under 100 ms,
resident memory under 180 MB).

Three facts the spec did not address:

1. **Capacity is temporal.** The same phone gives different capacity as it
   heats, drains and competes with other apps. A device tier is a prior, not a
   verdict.
2. **The users' phones sit low.** In Sri Lanka in September 2026 about 42% of
   Android web traffic ran on Android 13 or older and about 15% on 10 or older
   (StatCounter). The app's minimum is Android 9 (minSdk 28).
3. **Android signals differ by version.** Thermal status arrives at API 29,
   headroom and exit reasons at 30, frame deadlines and performance class at
   31 (checked against `api-versions.xml`, platform 35). From API 34 the system
   stops sending in-use memory trims.

The full design, feasibility and plan are in the Gurudevi Adaptive Runtime
document (Claude Docs, 2026-10-21); this ADR records the decisions.

## 2. Decisions

### D1. The runtime is a resource economy over three time layers

Seven accounts (cpu, gpu, memory, energy, thermal, network, storage). Supply is
read in three layers: baseline (what the device is), varying (what it can give
now) and realtime (what the app is spending). Demand is a registry of
workloads, each with a class, a quality ladder and a cost vector. An allocator
divides each account's budget among workloads in class order; the existing
governor (`packages/core/src/governor/`) is kept as its correction loop.

### D2. Four classes, mapped to the existing vocabulary

| Class | Spec `WorkCategory` | Glass priority | Shed |
| --- | --- | --- | --- |
| critical | `user-critical` | `critical` | never; degrades only inside its ladder |
| committed | `ui-transition` | `high`, `normal` | lowered, never removed |
| deferrable | `background-sync`, `media-prefetch`, `storage-cleanup`, `telemetry-flush` | none | postponed |
| ornamental | none | `low`, `decorative` | first |

The existing `admitWork` matrix and `VisualBudget` tiers remain the public
contract; they become views computed from the allocator's levels.

### D3. Native sensing is a Kotlin Expo module, not Nitro

`packages/verger-android` (formerly `apps/gurudevi-mobile/modules/runtime-sense`) measures and never decides.

- Decisions run on 500 ms windows and on state changes, so synchronous JSI
  access buys nothing. The cost that matters is how often anything crosses,
  and the module sends events only on change (an idle screen sends none).
- The Expo Modules API autolinks under CNG with no C++ toolchain, which fits
  the repo rule on native code and keeps it off the Tier 1 Nitro pin.
- The spec's figure of 70 to 120 ms per Expo call is not used here: it is not
  sourced in the audit and describes call volume, which this design avoids.
- Its own cost is not nothing: while visible it wakes about 70 times a minute
  (1 Hz thread sampling, memory every 10 s, headroom every 10–60 s); hidden, it
  stops. This cost is an outcome to measure against off, not an assumption.
- If a later phase needs per-frame synchronous access from a worklet, Nitro
  can be added for that one path without changing the policy layer.

The frame estimator is held to golden vectors generated by the TypeScript
reference, so both implementations produce the same windows.

### D4. Every signal has a fallback to Android 9

Polling of free memory and the low-memory flag covers API 34 and later, where
trims are withheld; a polled reading holds as a level until the next poll.
Planned, not yet built: battery temperature and frame-cost drift to infer heat
where thermal status is absent (API 28), and a confidence on each estimate that
widens the allocator's safety margin.

### D5. Invariants

1. Critical work is admitted first; its budget is reserved.
2. No workload is lowered for an account it does not spend.
3. Every change records its rule, signal and policy version. Field telemetry
   keeps the shape of each reason with its numbers removed (low cardinality,
   no fine timing fingerprint); exact values stay on the device's diagnostics.
4. Raising is slower than lowering; a failed raise doubles the wait.
5. Without signals the baseline holds; nothing guesses upward.
6. Native measures, TypeScript decides; every threshold has one source.
7. Gesture freeze: within 1 s of a touch or move, a hardware change that lowers
   quality waits and the last published values hold; a change that raises
   quality applies at once; heat (hot or worse) overrides the freeze. Scroll
   momentum after the finger lifts is not yet sensed.
8. Policies are deterministic and versioned; telemetry informs the next
   version, never the running one.
9. A workload enters the allocator only after its intrinsic cost is checked.

### D6. Evidence before closed loop

Three modes are built: off, shadow and active (closed loop); static and
minimal are planned. Assignment is a deterministic hash whose key includes the
policy version (the executive defaults to `adaptive-runtime-p<version>`;
`assignExperiment` is not yet called from the app); the kill switch turns the runtime off entirely, native sensing
included (shadow still runs the native module). Closed
loop reaches users only after shadow data from real phones, with a primary
outcome named in advance and guardrails (crashes, ANRs, low-memory kills,
heat, energy) that must not worsen.

### D7. Every phase passes five gates

Waste, hardware, scaling, telemetry and independent critique, as defined in
the design document. A gate that cannot be met is recorded as an open risk.

### D8. Pilot freeze

Until after the teacher pilot on 2026-10-26, only TypeScript changes behind
flags that default to current behaviour may merge. `runtime-sense` stays on
`feat/adaptive-runtime`.

### D9. A lieutenant to the OS, and a veteran of each phone

The runtime is a supervisor for this app only, subordinate to the Android
kernel: it never fights the scheduler or the memory killer, it acts before the
OS has to act bluntly (kill, uniform throttle, ANR), and it reports every
decision. It learns each phone as it is now, because system updates and vendor
policy change capacity after sale: after an OTA, apps run with only the
`verify` compiler filter until the daily idle-and-charging background dexopt
(AOSP ART Service configuration), and in 2022 Samsung's Game Optimizing Service
throttled apps by identity (XDA Developers, 2022-03-04). A per-device profile
keyed by the build fingerprint records frame, thermal, memory and per-thread
baselines; a new fingerprint marks it stale. Learned values move thresholds
only within bounds fixed by the policy version, so policies stay deterministic
while facts about the phone are learned. First panel: the Galaxy A52 and
Galaxy A24 and friends' phones, in shadow and active mode, before and after
their next update.

### D10. Shedding stops where it does not help

A lever is lowered only for a resource it relieves. Contention steps continue
only while each step measurably lowers the saturated thread's load; after two
that do not, the runtime stops and reports the contention as needing a code
fix. Quality rises only after calm frames are actually drawn, never on an idle
screen. Only levers with a consumer in the build are governed. A lever may
relieve several resources (the refresh cap relieves GPU, UI-thread CPU and
energy), but JS-thread contention counts only levers whose primary resource is
CPU work. A "not relievable" verdict holds until contention has been absent for
five saturation periods.

### D11. Verger: decoupled from any host

The runtime is named verger (the keeper of a sanctuary, who keeps it in order so the people
inside need not think about it) and lives in three host-neutral packages:

| Package | Holds | Depends on |
| --- | --- | --- |
| `@repo/verger-core` | reducer, runtime loop, telemetry, replay, experiments, host definition, built-in levers | nothing |
| `@repo/verger-android` | Kotlin Expo module: sensing, frame estimator, CPU attribution, hardware levers; the Android `RuntimePort` | verger-core |
| `@repo/verger-react` | provider, hooks, presence, long tasks, global reduced motion | verger-core; react, react-native, reanimated as peers |

A host describes itself as data with `defineHost({ name, levers, config })`. Each lever declares
its own rules (`requires` a capability, `whenHidden`, `whenIdle`, `whenWarm`, an `actuator`); the
reducer applies rules and never names a lever. A test fails if any host name appears in the
three packages, or if the reducer names its own built-in levers. Gurudevi is the first host:
`@repo/core/governor` holds its levers and its host definitions and re-exports verger, so
existing imports keep working; the mobile build mounts `GURUDEVI_MOBILE_HOST`, which governs
only the levers something applies today. Publishing outside the monorepo waits for device
evidence.

### D12. Recover, heal and grow across launches

Verger keeps a small record between launches and changes it only at boot (crash-only). At each
launch it reads the session marker the last process left, judges how that process ended
(Android `ApplicationExitInfo` from API 30; below that, a death while visible counts as a
failure), folds the result into the record, and decides how much of itself to run:

| Rung | Runs | Entered | Left |
| --- | --- | --- | --- |
| 0 | everything, with the learned profile | default | n/a |
| 1 | everything, profile ignored and reset | 2 failures in 24 h at rung 0 | 3 clean sessions |
| 2 | no hardware levers (refresh cap, CPU hints, global motion) | 2 more failures | 3 clean sessions, doubled per relapse |
| 3 | shadow: senses and decides, applies nothing | 2 more failures | as above |
| 4 | off, native code included | 2 more failures, or any death during native start | only a new policy version or app release |

Failures are crashes, native crashes, ANRs and excessive resource use. User stops and deaths
while hidden are not. A visible kill for memory (or by signal) is neither: it earns no clean
credit and gives back growth, because it is the very harm verger exists to prevent. Exits are
matched to the session by process id where both sides carry one. Sessions run with verger
off, sessions under another policy or release, and sessions already folded never move the
ladder; sessions shorter than 30 s in the foreground prove nothing.

The launch fails closed at every step (revised after the hostile review of 2026-10-21):

1. If the store cannot be read, verger stays off and writes nothing; a corrupt record starts
   at rung 3, never rung 0.
2. Whether verger may touch native code is decided from the store alone: a session that died
   in its `starting` stretch, or a record on rung 4, ends the launch before any native call,
   so a native fault cannot loop.
3. The `starting` marker is written and the write confirmed before any native call; if it
   cannot be written, verger stays off.
4. Facts, judgement, decision and start run in one synchronous stretch, and the `running`
   marker and the record are confirmed before any host code runs.
5. An exception anywhere leaves an explicit `off` session behind.

The accepted cost: an unrelated native crash inside the starting stretch also sends the
device to rung 4 until the next release, which fails closed.

Healing and growth sit on the ladder. Trust in the learned profile halves on a failure and
grows by 0.1 per clean session. The profile is keyed by a hash of the OS build fingerprint, so
a system update relearns it. It holds a starting point (the moving average of where the closed
loop held each lever, used as whole levels rounded down, at trust 0.6 or more), which enters
the bottom of the loop's stack and is given back after the loop's own decreases. The profile
learns only from the loop's own pressure, plus what it kept of the starting point while frames
were not calm, and only over time when frames were drawn, so a starting point held on a still
screen is never evidence for itself; and a grant that relaxes capacity floors
one step after three proving sessions (cool, roomy, under 5 % stressed, at trust 0.8 or more),
given back at once on strain. Preference, accessibility, capability and containment floors are
never relaxed. A configurable exercise share runs healthy launches without hardware levers so
the degraded paths stay used. The last 48 decisions are kept in a flight recorder and sent once
after a failed session; summaries report the quality given up beside the performance gained.

`createVerger` in verger-core owns the launch; hosts supply a `VergerPlatform` (facts, exits,
port) and a `VergerStore` (Gurudevi uses AsyncStorage, because MMKV stays off its startup path).
Policy version 4.

### D13. The stage before the chairs (2026-10-24)

Verger is built as a full horizontal foundation of ten layers (sense, estimate, demand, decide,
act, activate, observe, learn, recover, lab), each behind a contract and replaceable. Specific
choices (release preset, thresholds, governed levers, telemetry destinations) are data or
plug-ins placed later on evidence, never constants in logic. Development builds expose and
change every layer live, as events, so sessions replay exactly. Rules and the list of open
choices: `docs/engineering/runtime-performance/verger/stage-and-chairs.md`. Activation
(`activation.ts`) is the first layer built under this rule.

## 3. Consequences

- The facade in the spec keeps its names; its internals change.
- A registry test will fail when a component animates, decodes, fetches or
  schedules without declaring a workload.
- Telemetry carries the policy version, a config hash, a session id and a
  device stratum; state and lever events are capped at 64 per launch and
  summaries separately at 120. A per-day byte budget is not yet enforced; the
  review estimated at most about 19 KB per launch.
- Thresholds tuned on the Galaxy A52 are provisional until checked on a 2 to
  4 GB phone or constrained emulators.

## 4. Alternatives considered

| Alternative | Rejected because |
| --- | --- |
| Nitro module for sensing (the spec) | synchronous access is not needed at window granularity; adds C++ build risk on a Tier 1 pin |
| Visual-only adaptation (as in `expo-adaptive-glass`) | most of Gurudevi's cost is sync, storage, images and the JS thread |
| Fixed device tiers | the same device varies more within a session than tiers differ |
| Self-tuning policies | non-deterministic, unreproducible; rejected by the telemetry ledger |
| A C++ estimator shared across platforms | iOS is out of scope; golden vectors give parity without it |
