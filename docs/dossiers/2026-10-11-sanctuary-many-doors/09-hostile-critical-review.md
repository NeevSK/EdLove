# Hostile Review: Break the Claims Before People Depend on Them

## Possibility worth defending

An expansive Sanctuary is worth exploring because educational life crosses interfaces, institutions, and decades. The reviewer protects that possibility by exposing claims that would betray the people relying on it. Skepticism should demand experiments, not reduce ambition to today's feature list.

## Claims under attack

| Claim | Brutal objection | Evidence or design that answers it |
| --- | --- | --- |
| “One ecosystem, many doors” | Many doors can become nine copies of broken business logic | One real effect with consistent policy/receipt through two clients |
| “Core is sovereign” | Operator credentials, provider policy, auth, DNS, and billing still control operation | Dependency map, export/restore drill, documented switching path |
| “Offline means resilient” | Phone loss, revoked permissions, stale records, and conflicting edits persist | Restart, account isolation, conflict, device-loss scenarios |
| “Distribution removes failure” | It adds coordination, patching, keys, routing and correlated outages | Failure-domain assessment and funded operational ownership |
| “AI only assists” | Synthetic counts and success copy already present unsupported facts | Unknown-field preservation and exact reviewed effects |
| “Confirmation is safe” | Old/generic buttons can approve the wrong proposal | Version-bound confirmation and expiry/replay tests |
| “Durable agents” | A run can persist without reaching its runner | Crash at each handoff; restart repair and receipt convergence |
| “Mesh works” | Current broadcast methods return counts without network transfer | Actual physical-device transport, packet capture and restart tests |
| “Encryption is security” | Public school IDs and hashes do not authenticate teachers | Secret entropy/key custody, sender authentication, malicious-peer proof |
| “WhatsApp is the easiest path” | Linking/correction/browser jumps may create work | Observed task effort and current telco/account capability checks |
| “Cheap infrastructure” | Unpaid support/maintenance hides cost | Fully loaded cost and operator replacement model |
| “School data is ground truth” | Seeded examples and modeled ratios can misrepresent living conditions | Provenance, date, uncertainty, and challenge/correction process |

## Severity by user consequence

**Pilot blockers for the affected workflow:** unsupported save success; invented voice facts; unverified actor/scope; accepted-message loss; secretless production ingress; live SQL path unproven; no accountable owner for disputed records. Restrict a prototype to disclosed fictional/demo data until these are resolved. This is a recommended release boundary, not an instruction to delete existing routes.

**Growth blockers:** no measured restore; retry storms; missing operator coverage; uncontrolled cost; weak per-tenant isolation; inaccessible or untranslated recovery; migration failures; ordinary users needing staff help for every correction.

**Future gates:** product MCP consent, assistant platform invocation, local hub operations, cell routing, federation governance, and offline delegated authority. These are research tracks, not reasons to hold all useful private tools hostage.

## Counterexamples that defeat the initial recommendation

The modular-application default is wrong if a real institution requires independent custody and funded local operation now. A voice-first pilot is wrong if correction takes longer than a short manual form. WhatsApp-first is wrong for a participant group that does not use it or whose linking/privacy constraints cannot be resolved. Hosted-only is wrong if outage duration repeatedly exceeds a tolerable workflow window. “More channels” is wrong if core receipt semantics are still inconsistent.

The default architecture therefore remains provisional. Conditions, not slogans, select the path.

## Failure injections with non-negotiable questions

Terminate the worker immediately after provider acceptance. Restart API after webhook acknowledgement. Reuse one operation key with different content. Confirm an expired draft. Remove a teacher bond while a device is offline. Switch accounts with queued work. Flood one tenant. Corrupt a migration then restore. Lose the person who knows the credentials. Ask an agent to export all learner records through a malicious document. Transfer an institution to another operator.

For each: where is the work, who can read it, what will the user believe, who repairs it, how long can it remain pending, and what evidence prevents silent loss? A diagram does not answer these questions.

## Hard tradeoffs the documents cannot dissolve

Offline reading can outlast permission revocation. A highly available shared store can still concentrate stewardship power. A backup preserves data but can retain material marked for deletion. A convenient channel exposes metadata to its vendor. Manual human review preserves agency but can become unpaid checking labor. Adding provider alternatives helps only if credentials, data portability, testing, and operators are ready.

“Low friction” cannot mean hiding these consequences. It should mean handling ordinary complexity on behalf of the user and revealing the choice when it matters.

## Documentation self-critique

This dossier can become a sophisticated substitute for delivering one useful workflow. Its breadth is justified only if the evidence ledger, decision rounds, and milestones narrow the next experiment. Nine perspectives written by one author are vulnerable to shared blind spots. Real teachers, parents, students, school stewards, independent security/database reviewers, and measured incidents must challenge it.

No forecast below establishes performance or staffing capacity. No source inspection establishes exploitability or deployment. No scientific-sounding metaphor replaces data. Maintain the boundary between a living school and the passive software artifact supporting it.

## Integration round R8

Keep the vision; withdraw unsupported guarantees. Advancement requires named evidence, owner, affordable operation, and an exit condition. Preserve alternatives with explicit triggers, and suspend a channel/effect when its user consequences cannot be made truthful. The final product plan must prioritize the dangerous gaps before extending protected access and make abandoning a bad experiment an acceptable outcome.
