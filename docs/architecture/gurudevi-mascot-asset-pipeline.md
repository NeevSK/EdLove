# Gurudevi Mascot Asset Pipeline

## Purpose

This document is the implementation contract for the Gurudevi mascot family. Figma is the visual source of truth; `@repo/ui` owns the semantic renderer and the product-facing API; exported files are build inputs, not independent designs.

The mascot family is intentionally open-ended: new roles, states, and media formats may be added without changing every feedback surface. The shared identity remains the same firefly family, while role and platform dialects remain explicit.

## Source-of-truth layers

1. **Figma vector master** — canonical anatomy, proportions, light/dark art variants, expressions, poses, and props.
2. **Exported static assets** — approved SVG, PNG, and WebP files generated from the master.
3. **`@repo/ui` semantic model** — typed role/state/theme/scale inputs and accessibility behavior.
4. **Platform renderer** — SVG or image rendering today; optional animation adapter later.
5. **Product surfaces** — feedback, onboarding, role spaces, and narrative web compositions.

Never edit an exported asset by hand and never regenerate a single pose independently. Changes begin in the Figma master, then flow through exports and visual QA.

## File types and intended use

| Format | Use | Rule |
|---|---|---|
| `.fig` / Figma library | Source artwork and components | Only canonical design source |
| `.svg` | Web, Figma, scalable scene art | Use when the artwork remains visually correct as vector |
| `.png` | Mobile scene or complex illustration fallback | Export at approved scales; preserve transparency |
| `.webp` | Web/mobile performance fallback | Use for raster artwork where SVG is too expensive |
| `.riv` | Future interactive character animation | Add only after static anatomy and state timing are approved |
| `.json` Lottie | Future timeline animation | Use only for finite, non-interactive moments |

The first production milestone is static SVG/PNG/WebP. Rive and Lottie are extension formats, not alternate sources of truth.

### Current approved visual input

The current approved visual input is the supplied Gemini artwork, not the
earlier hand-built SVG experiments:

```text
apps/gurudevi-mobile/assets/mascot/
  Gemini_Generated_Image_ezd4cqezd4cqezd4.jpg  # single guide artwork
  Gemini_Generated_Image_oaffwaoaffwaoaff.jpg  # pose sheet / state reference
  image.webp                                    # smaller guide derivative
```

These files are preserved byte-for-byte and are not traced, recolored,
cropped, or regenerated by the runtime. The high-resolution single guide is
currently injected through `MascotProvider` and rendered by the shared
`FireflyMascot` component. That is deliberately a one-artwork integration
milestone: it closes the documentation-to-visual gap without pretending that
the pose sheet has already been exported into individual production assets.

The pose sheet is reference material until each pose is exported separately
from the original artwork and reviewed at inline, card, and scene sizes. No
state-specific crop should be made in code because that would make the visual
quality depend on device layout and would include the sheet labels.

## Repository layout

Approved exports belong under:

```text
packages/ui/assets/mascot/
  firefly-guide-guiding-light-card.svg
  firefly-student-curious-light-card.svg
  firefly-teacher-resting-light-scene.svg
  firefly-guide-guiding-dark-card.svg
  ...
```

The directory also contains `manifest.json`. It is intentionally empty until
the vector master is approved; this makes the missing production art visible
to tooling and reviewers instead of silently treating concept art as shipped
art.

Run `pnpm --filter @repo/ui validate-mascot-assets` after exporting. The
validator checks the filename grammar, duplicate IDs, Figma source references,
supported extensions, and that every exported file is registered. Review
entries are allowed; only the visual approval process may promote them to
`approved` or `production`.

The current generated character sheet at `packages/ui/assets/images/gurudevi-firefly-character-sheet-v1.png` is concept reference material and must not be imported as the runtime mascot.

The current runtime artwork is app-owned because it is still raster artwork
under review. `@repo/ui` accepts it as an injected `MascotArtworkSource`, so
the shared component stays platform-neutral and the app can later replace the
source with approved per-state exports without changing every caller.

The naming contract is implemented by `mascotAssetId()` and `mascotAssetPath()` in `packages/ui/src/components/mascotAssets.ts`:

```text
firefly-{role}-{state}-{theme}-{scale}.{format}
```

## Runtime integration

The public semantic seam is:

```tsx
<Mascot
  mode="glowing"
  role="student"
  state="curious"
  theme="light"
  size={48}
/>
```

Existing callers may continue using `mode="glowing" | "resting" | "offline"`. The renderer maps those legacy modes to semantic states. New surfaces should prefer `role`, `state`, and `theme`.

`MascotProvider` can supply default role and theme for a surface. `FireflyFeedbackScene` owns the path / scene composition but delegates the actual character to `Mascot`, so there is one shape system instead of a compact renderer and a second large renderer drifting apart.

## Preserving one shape system

The character master must keep these invariant across every role and state:

- head-to-body ratio;
- eye placement and expression grammar;
- wing attachment and maximum spread;
- abdomen glow placement;
- contour thickness and corner softness;
- minimum readable silhouette at 48px;
- light/dark palette relationship.

Roles may change posture, gaze, accent color, and one or two props. They may not change the species, core face, wing anatomy, or illustration quality.

## Refinement workflow

1. Annotate the current implementation mismatch against the supplied artwork.
2. Keep the original raster artwork as the visual reference; do not redraw it
   in SVG merely to satisfy the asset contract.
3. Export one pose per file from the artwork source, without sheet labels or
   layout-dependent crops.
4. Refine the master in Figma only after the user approves the visual family.
5. Validate light mode first on vellum, silk, quiet, and elevated surfaces.
6. Validate dark mode on ink, shroud, and bioluminescent surfaces.
7. Test 24px, 48px, 96px, and 240px exports.
8. Export only approved combinations and update the manifest.
9. Run visual and accessibility checks.
10. Replace runtime assets only after review.

This keeps visual refinement open-ended without allowing ad hoc edits to fragment the family.

## Animation path

Animation is layered on top of the same static anatomy:

- **Reanimated / CSS:** breathing, arrival, drift, and glow opacity for lightweight feedback.
- **Lottie:** finite celebration, bloom, or onboarding moments with no user-controlled branching.
- **Rive:** future interactive guide states where the character responds to progress, hover, drag, or user input.

The semantic state model remains independent of animation format. If animation is unavailable, reduced, or disabled, the same static state asset and accessible copy remain visible.

Do not add Rive or Lottie files until a real interaction requires them. This avoids a second animation state machine that can disagree with `fireflyFeedback.ts`.

## QA and acceptance

- Every asset has a role, state, theme, scale, format, and source reference.
- Light mode passes before dark mode is approved.
- The silhouette remains recognizable without glow.
- Static fallback exists for every animated state.
- Reduced motion never removes status meaning.
- Web and native use the same semantic inputs but may choose different file formats.
- No role or state is represented only through color.
- New art is independently created and reviewed for brand/IP similarity before release.
