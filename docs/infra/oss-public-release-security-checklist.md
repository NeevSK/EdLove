### The `.gitignore` blind spot

`.gitignore` only governs **untracked** files. Anything already tracked stays
tracked forever, and force-adding (`git add -f`) bypasses it silently. This
repository has **91 tracked files that its own `.gitignore` claims to exclude**
(`git ls-files -c -i --exclude-standard`). `.gitignore` is therefore *not* an
inventory of what is published, and any audit that greps `.gitignore` for
sensitive patterns is auditing the wrong thing.

Three groups matter:

| Group | Count | Risk |
|---|---|---|
| `apps/gurudevi-mobile/supabase/.temp/*` | 8 | Generated by `supabase link`. Publishes the **production** project ref `qzoawolfkuwiuyaoiybz` and pooler host `aws-1-ap-south-1.pooler.supabase.com` (Mumbai). The password is **not** present in `pooler-url`, so this is reconnaissance, not a credential — but it hands an attacker the exact project and region to target. |
| `packages/analytics/src/**/*.js`, `*.d.ts`, `*.d.ts.map` | 64 | Compiled output committed next to its TypeScript source, and `packages/analytics/package.json` exposes a wildcard export `"import": "./src/*.js"`. A pull request can therefore modify **only the `.js`** and change what consumers load while review focuses on the `.ts`. This is a code-review bypass, and violates OSPS-QA-05.01 (version control must not contain generated executable artifacts). |
| `apps/gurudevi-mobile/temp/device-*.png`, `device-*.xml` | 9 | Device screenshots and UI-hierarchy dumps from a platform serving **minors**. Requires manual review for student data before publication. |

Also tracked and needing a decision: `.agents/scratch/tasks.md`,
`packages/core/scratch/*.cjs`, duplicate `profile.ts` under
`packages/community/src/` and `packages/core/src/api/`, and five `.env.example`
files (content is fine; the tracking pattern is the issue).

Remediation is `git rm --cached` plus a `.gitignore` audit — see §1.7.

### Risk profile

This is not a generic SaaS monorepo. It handles **minor's school students and
children**, parent/guardian identities, teacher assessments, attendance,
in-platform messaging, and payments. Publishing the source raises risk in two
directions at once:

1. **Source-disclosure risk** — architecture, authz model, policy evaluation
   logic, and data contracts become readable by adversaries and by people who
   will never be your users.
2. **Supply-chain / contributor risk** — the repository becomes an untrusted
   input surface: forks, pull requests, Dependabot/Renovate, GitHub Actions
   from forks, and issue content all become code-execution or social-engineering
   vectors against your infrastructure.

Child-data handling raises the compliance bar above the usual OSS baseline. See §10.

### 1.1 Full-history secret scan

The working-tree pattern scan was clean. History was not scanned. Deleted
secrets are the single most common OSS breach root cause.

```powershell
# Whole-history scan (this is the gate; the earlier grep was not sufficient)
gitleaks detect --source . --log-opts="--all" --redact --report-format json --report-path reports/gitleaks-history.json

# Then confirm the scanner itself is wired into CI, not just run once by hand
pnpm run audit:secrets          # verifies Doppler config, NOT history — see §2.1
```

Also verify the `.gitleaks.toml` allowlist is empty or justified. An allowlist
that has grown to suppress findings is a control that has stopped working.

```powershell
Get-Content .gitleaks.toml | Select-String -Pattern "path|regex|commit" -Context 0,1
```

If a real secret is found: **rotate it first, then rewrite history.** Rewriting
without rotating leaves a live credential in every fork and clone.

| Secret class | Rotate at |
|---|---|
| Supabase service-role / secret keys | Supabase dashboard → project settings |
| Doppler service tokens | Doppler → project → service tokens |
| Sentry auth token | Sentry → organization settings |
| Cloudflare API token | Cloudflare → My Profile → API Tokens |
| EAS / Expo tokens | Expo dashboard |
| Payment provider (PayHere) keys | Payment provider dashboard |
| Google OAuth client secret | Google Cloud console |
| Android keystore + Play service account | Play Console + local keystore backup |
| GrowthBook SDK key | GrowthBook settings |

### 1.7 Un-tracking ignored-but-committed files

`.gitignore` is advisory. The authoritative inventory is what git actually
tracks, so the audit and the fix both operate on the index, not on the ignore
file.

```powershell
# What is published despite being ignored
git ls-files -c -i --exclude-standard

# Un-track without deleting from disk
git rm --cached -- apps/gurudevi-mobile/supabase/.temp
git rm --cached -- packages/analytics/src
git rm --cached -- apps/gurudevi-mobile/temp

# Prove the fix
git ls-files -c -i --exclude-standard   # must be empty
git check-ignore -v apps/gurudevi-mobile/supabase/.temp/project-ref  # must match a rule
```

Then confirm the ignore rules actually exist for each path, because `.gitignore`
currently has no rule covering `supabase/.temp`, `apps/*/temp/`, or
`packages/**/*.d.ts.map` — those files are excluded only by a broader pattern
that may change without warning.

Commit these removals **before** the visibility flip, but remember they do not
clean history. Anything previously pushed remains in the object store and in
every clone; §1.1 full-history scanning is still the gate. See §13.1 for why
rotation precedes history rewriting.

Deleting `packages/analytics/src/**/*.js` from the index is safe **only** after
confirming nothing imports the `.js` form directly and that the build emits to
`dist/`:

```bash
git grep -n -E "from ['\"][^'\"]*analytics/src/[^\"']*\.js['\"]" -- '*.ts' '*.tsx'
```

## 2. Secrets management

### 2.1 Understand what the existing tooling does

`pnpm run audit:secrets` maps to `node scripts/verify-doppler-config.mjs
--scope workspace`. Despite the name, it **verifies that the Doppler config
contract is satisfiable** — it does not scan for leaked credentials. Secret
scanning is a separate concern, handled by `.gitleaks.toml` (§1.1) and
`audit:security`. Do not let the similar names create a false sense of coverage.

### 2.2 Doppler posture

Doppler is the declared source of truth for runtime secrets. Environment model:
`dev` / `stg` / `prd` under project `gurudevi-mobile`.

- [ ] Rotate every credential that was ever present in the repository, even if
      currently untracked — rotation is the only control that survives history.
- [ ] Each Doppler config uses scoped **service tokens**, not personal tokens
      (`docs/infra/doppler-secrets-management-guide.md` §Security Best Practices).
- [ ] Service tokens are per-environment and read-only where write is not needed.
- [ ] Personal access revoked for accounts no longer required.
- [ ] Doppler audit log reviewed for unexpected reads.
- [ ] `machine-only` / `restricted` visibility applied to AI-agent-consumed and
      production secrets as the guide already prescribes.
- [ ] Secrets referenced by **name only** in the public repo. Values must never
      appear in a workflow, a default, or a fallback.

### 2.3 Public-secret classes that are safe by design

These are publishable and should be documented as such so contributors do not
"fix" them:

| Value | Why it is public |
|---|---|
| `EXPO_PUBLIC_SUPABASE_URL` | Public project URL |
| `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Supabase publishable key — RLS is the control |
| `EXPO_PUBLIC_POSTHOG_API_KEY` | Write-only analytics key |
| `EXPO_PUBLIC_SENTRY_DSN` | Public ingestion endpoint |
| `EXPO_PUBLIC_GROWTHBOOK_CLIENT_KEY` | Public SDK key |
| `EXPO_PUBLIC_WEB_PUSH_VAPID_PUBLIC_KEY` | Public by definition |

The critical corollary: **RLS and authorization policy are the entire security
boundary for these.** Public keys mean a browser or a patched APK can call any
Supabase RPC. This makes §5 (authorization) a release blocker rather than a
nice-to-have.

## 3. Repository attack surface created by going public

Publishing converts the repo into an input surface. Each item below is an
independent control.

| Control | Requirement | Status |
|---|---|---|
| Workflow privileges | **5 of 12 workflows declare no `permissions:` at all**: `pr-guard.yml`, `quality-gate.yml`, `storage-contract.yml`, `deploy-canary.yml`, `sentry-sourcemap-upload.yml`. Add least-privilege `permissions:` to each; set `contents: read` as the repo default in GitHub settings so a new workflow is safe by default | [ ] |
| Dangerous triggers | Verified **absent**: no `pull_request_target`, no `workflow_run`, no `secrets: inherit`, no `issue_comment`-triggered execution, no self-hosted runners. Re-check on every new workflow | [ ] |
| Checkout credentials | Use `persist-credentials: false` on `actions/checkout` in any workflow that also runs untrusted code, so the token is not left in `.git/config` for a later step to exfiltrate | [ ] |
| Fork PR secrets | GitHub does not expose secrets to fork PRs; verify no workflow assumes otherwise | [ ] |

### 4.5 pnpm supply-chain posture

`pnpm-workspace.yaml` is the control plane for every install in this repository,
so its settings are security settings.

| Setting | Current | Assessment |
|---|---|---|
| `minimumReleaseAge` | `0` | **Disables the publish cooldown.** pnpm defaults this to 1440 minutes (24h); the community-agreed floor is 4320 (3 days). ## 5. Identity, authorization, and tenant isolation

This is the highest-value target in this repository. Authz logic lives in
`packages/policies` (Cedar policies), `apps/sanctuary-api` (authorization
middleware), and `packages/core` (permission snapshots), and is enforced
server-side plus by Supabase RLS.

Because the Supabase publishable key is public (§2.3), **RLS is the only thing
standing between an attacker and the database.** Client-side Cedar checks are
UX, not security.

- [ ] Every table has RLS enabled. A table with RLS disabled is a full read/write
      hole reachable with a public key.
- [ ] RLS policies have **positive and negative** tests: allowed role succeeds,
      wrong role denied, missing tenant scope denied, stale scope denied.
      `production-readiness-program.md` §F already requires this; it is
      unreplicated here only if it is unreplicated there.
- [ ] Authorization parity audit is green: `pnpm run audit:authorization-parity`
      (Cedar ↔ ZenStack ↔ runtime).
- [ ] No authorization decision is made only on the client. Audit
      `gurudevi-mobile` for permission checks that gate UI without a server-side
      counterpart.
- [ ] Permission snapshots are re-validated server-side, not trusted from the
      client after issuance.
- [ ] Account-scoped runtime: switching accounts closes the previous runtime
      before opening the next (already in the readiness program §G).
- [ ] Cross-tenant tests use **two real accounts** and assert isolation in both
      directions, per `[AUTHZ]` mode in `production-evidence-governance.md`.

Evidence requirement: this section may not be closed on unit tests alone.
Per `production-evidence-governance.md`, mocked authz is **G1 boundary evidence**
and cannot be reported as G2+ or R1. Use `[AUTHZ]` + `[INT]` against a real
database.

## 11. Evidence and reporting standard

Per `AGENTS.md` and `production-evidence-governance.md`, no security claim is
closed by an unqualified "tests passed".

- Every gate row in §1 and every **R** row in §9 requires the exact command,
  the engine and runtime version, the evidence level (G0–G5/R1), the scenarios
  exercised, and what the result does *not* prove.
- Mocked security tests are **G1 boundary evidence**. They do not demonstrate
  that RLS, rate limits, or webhooks hold against a real attacker.
- Authorization and isolation conclusions require `[AUTHZ]` + `[INT]` against a

- Anything not exercised is `not started` or `blocked` — never silently omitted.

Report format:

```text
G<level> <engine+version> — <command> — <scenario>: <n>/<n> passed.
Proves: <what the assertions actually establish>
Does not prove: <untested platforms, failure paths, attack classes>
Residual risk: <what remains unproven>
```

## 12. Commonly forgotten controls

Everything above is a control you can name from a checklist. This section is
the residue — the things that reliably go missing in repositories like this one,
each with the external guidance that establishes it as a real requirement rather
than a preference. Treat it as the second pass after §1–§11 are green.

### 12.1 Rotation precedes history rewriting

The instinct is to scrub the secret from history and move on. That is the wrong
order. GitHub scans newly public repositories within seconds, and orphaned
commits remain reachable **by SHA** in GitHub's object graph even after a force
push or repository deletion. Rewriting history does not retract a credential
that has already been indexed.

So: **rotate first, verify the old value is dead, then rewrite.** Everything in
the §1.1 rotation table applies, and each row needs a "old value rejected"
observation, not a "PR merged" observation.

### 12.2 `SECURITY.md` and `security.txt` are different things

Both are expected. Most projects ship one and assume they shipped both.

| | `SECURITY.md` | `security.txt` (RFC 9116) |
|---|---|---|
| Scope | one repository | one domain |
| Location | repo root or `.github/` | `https://<domain>/.well-known/security.txt` |
| Transport | any | HTTPS only |
| Machine-readable | no | yes — `text/plain`, RFC 5322 fields |
| Enables GitHub private reporting | yes | no |

- [ ] `SECURITY.md` exists (it does — validate per §1.5).
- [ ] `/.well-known/security.txt` is served by `gurudevi.app`, `edlove.org`, and
      the marketing site, each with at minimum `Contact:`, `Expires:`,
      `Canonical:`, and `Policy:`.
- [ ] `Expires:` is a real future date and is re-checked on a schedule. A stale
      `security.txt` is worse than none because it advertises a dead channel.
- [ ] Scope is understood: a `security.txt` on the apex domain does **not** cover
      subdomains. Each public host needs its own, or a documented redirect.

### 12.3 OSPS Baseline vs OpenSSF Scorecard vs best-practices badge

Three different things that get conflated into "we ran a security scan".

- **OpenSSF OSPS Baseline** — 41 controls across Branch, Build & Release,
  Code, Dependencies, Identity, Logging, Project, Quality, Security, and
  Verification. Three levels; **Level 1 is the right target for a
  single-maintainer project**. This document is written against it.
- **OpenSSF Scorecard** — automated repository-level posture, scored across
  Branch-Protection, Pinned-Dependencies, Signed-Releases, Security-Policy,
  Token-Permissions, and more. Its `Pinned-Dependencies` check is the automated
  version of §4.2.
- **OpenSSF Best Practices badge** — driven by a `.bestpractices.json` file in
  the repo root. Cheap to add, and it makes the public posture legible without a
  README claim.

- [ ] Adopt `.bestpractices.json` at Level 1 and treat the badge as earned, not
      as decoration.
- [ ] Run Scorecard after §1 and §3 close; fix what it finds rather than
      explaining it away.
- [ ] Map each OSPS Baseline control you claim to the local check that
      evidences it, per §11.

### 12.4 Dependency tooling overlap

Both `.github/dependabot.yml` and `renovate.json` are configured. Running two
autobots produces duplicate and conflicting PRs, doubles review load, and — worse
— trains maintainers to reflexively close bot PRs, which destroys the signal for
the one that matters.

- [ ] Pick one as the source of update PRs. Keep the other only for a
      non-overlapping ecosystem, documented.
- [ ] If Dependabot is kept, add the `github-actions` ecosystem (missing today).

### 12.5 Three scanners that are not interchangeable

Dependabot alerts, secret scanning, and code scanning catch different classes
and none implies the others. "We have Dependabot" is not coverage.

- [ ] Name, in `SECURITY.md` or a maintainer doc, which scanner covers which
      class: known dependency CVEs, leaked credentials, and unsafe code patterns.
- [ ] Confirm each is actually enabled on this repository, not merely configured
      on an account.

### 12.6 `allowBuilds`, `postinstall`, and install-time code execution

Modern package managers made this the default threat: a dependency's
`postinstall` runs arbitrary code the moment anyone installs. pnpm ≥10 disables
lifecycle scripts unless allowlisted, and this repository uses that allowlist
(`allowBuilds`, §4.5) — which is the correct posture.

The oversight is that the allowlist then grows to 30 entries without anyone
reading it, because the alternative is a confusing build failure. Treat each new
`allowBuilds: true` as a security decision requiring the same review as a
dependency addition.

### 12.7 Provenance, SBOM, and "just publish the source"

Source-only release still needs an inventory. A consumer of this code — including
yourself in a year — cannot answer "which versions of what ended up in this
app" without one.

- [ ] Emit an SBOM (CycloneDX or SPDX) per released app, not per package.
- [ ] Record where each app is deployed and from which commit
      (SLSA provenance for build outputs).
- [ ] Publish a checksums file for any distributed binary (§8.1).

### 12.8 `.gitignore` is not an inventory

Covered in detail at §0 and §1.7 because this repository fails it concretely,
but the class of bug generalises: `.npmignore`, `.dockerignore`, the `files`
array in `package.json`, CI artifact retention, and Expo/EAS build output are all
separate publishing surfaces with separate ignore files. Audit each one.

### 12.9 Root MIT does not reach your dependencies or your data

Stated once in §4.4 and §10.3 because it is the most common legal
misunderstanding in a monorepo flip: the root `LICENSE` covers first-party source
only. It does not relicense `@shopify/react-native-skia`, does not grant rights to
fonts or icons, and does not grant redistribution rights to a harvested research
corpus.

### 12.10 Copyright is not trademark

Making the repository public publishes the **source**. It does not license the
`Gurudevi` / `EdLove` / `Sanctuary` names or logos for third-party use, and it
does not make "Gurudevi" a trademark.

- [ ] `TRADEMARK.md` stating what is and is not licensed by the public repo.
- [ ] Decide whether the logo files may be redistributed at all.

### 12.11 Accidental publication of internal packages

Every `@repo/*` package is a publish candidate by default.

- [ ] Each package that must **not** reach npm sets `private: true` or an
      explicit `publishConfig.access` / `publishConfig.registry` guard.
- [ ] Audit the scoped namespace and any org-level publish rights.
- [ ] Confirm `files` in each `package.json` does not ship `.env`, tests with
      real data, or internal docs.

### 12.12 What a PR reveals about its author

Publishing invites strangers. `CONTRIBUTING.md` should state that a pull request
exposes the author's name, email, and device metadata to the public.

- [ ] State it plainly in the contribution guide.
- [ ] Do not require contributors to email the maintainer privately.
- [ ] Note that CI runs on untrusted code, so contributors should expect their
      PR to execute in a GitHub-hosted runner.

### 12.13 Governance documents that nobody remembers

Present: `LICENSE`, `SECURITY.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`.
Missing and commonly forgotten:

- [ ] `GOVERNANCE.md` — who can merge, who can release, how disagreement resolves.
- [ ] `SUPPORT.md` — where questions go, separate from vulnerability reports.
- [ ] `CITATION.cff` — for an education-research-adjacent project this matters.
- [ ] `.github/CODEOWNERS` — mandatory review on authorization paths (§3).
- [ ] `.github/ISSUE_TEMPLATE/` — **security-sensitive**: a public bug report is
      the wrong channel for a vulnerability. Templates should redirect reporters.
- [ ] `.github/PULL_REQUEST_TEMPLATE.md` — requires the evidence block from §11
      and the AI-disclosure line from §10.5.

### 12.14 The two-person rule on irreversible operations

Solo-maintainer reality: there may not be a second person. Then the control is
substitution, not omission.

- [ ] Visibility flips, history rewrites, first public release, and signing-key
      operations require a deliberate, dated, recorded action — not a muscle-memory
      command. §13 is that record.
- [ ] Where a second maintainer is unavailable, require a cooling-off period or
      an external reviewer for the irreversible ones.

### 12.15 Abandonment plan

A public repository with minors' data and payment integrations needs a stated
answer to "what happens if you stop maintaining this?"

- [ ] Published `SECURITY.md` **supported-versions** table is the mechanism.
- [ ] Data deletion path must survive the maintainer leaving (§6.3) — otherwise
      students' records are orphaned permanently.
