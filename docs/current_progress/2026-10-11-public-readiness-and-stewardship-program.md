# Public Readiness & Stewardship Program

## Outcome

Prepare Gurudevi for an intentional public repository opening and for accepting
aligned support, while preserving user safety, source integrity, and the
Sanctuary boundary. This is a readiness program—not a claim that the repository
is already public or that revenue systems are live.

## Public Narrative

Gurudevi is an offline-first educational ecosystem and private digital
sanctuary for Sri Lankan schools, teachers, students, and households. It reduces
administrative burden and dependence on stable connectivity without making user
attention or data the price of care. Its short introduction is
[What Is Gurudevi?](../Core/what-is-gurudevi.md), followed by the expanded
[Gurudevi Soul & Core Covenant](../Core/gurudevi-soul-and-core-covenant.md).

## Readiness Gates

| Gate | Required evidence before public opening or external contributions |
| --- | --- |
| Repository safety | Secrets, private data, generated credentials, internal-only endpoints, and sensitive history are reviewed; no live secret is committed. |
| Legal clarity | License, contributor terms, trademark stance, copyright provenance, and third-party notices are published and internally consistent. |
| Contributor path | A newcomer can install, run a bounded verification command, report a vulnerability privately, and understand review expectations. |
| Public documentation | README, architecture map, product definition, support covenant, roadmap status, and contact routes state only what is true today. |
| Operations | Owners, incident response, dependency updates, release/rollback, and support boundaries have named, sustainable practices. |
| User protection | Privacy, child safety, data retention/export, and public-community moderation policies are checked before exposing live services or inviting accounts. |
| Rewarded-attention stop-ship gate | No live sponsor-media release until real SDK playback, authenticated balance access, cryptographic server-side verification, replay tests, child/ATT controls, and a production-like end-to-end test have evidence. |

## Ordered Work

1. Establish a clean release candidate from the current working tree; do not
   publish a dirty or unreviewed state.
2. Run a secrets and sensitive-data review, including git history and build
   artifacts; rotate anything that may have escaped.
3. Reconcile the public README and every public claim with current, verifiable
   product state.
4. Publish the support covenant and a lightweight funding disclosure format
   before accepting material support.
5. Validate installation, tests, security reporting, and contributor flow from
   a fresh machine/account perspective.
6. Obtain explicit founder approval for repository visibility, public issue
   tracking, contributor intake, and the first external support channel.
7. Only then change external hosting or repository visibility settings.

## Sponsor-Media Boundary

The Energy Reservoir may help users acquire optional AI capacity without direct
payment, but it is never a condition of core access. It is not approved for
groups, community feeds, direct messages, notifications, classroom workflows,
or any other product surface. See the
[Rewarded Ad Center Policy](../decisions/2026-08-31-rewarded-ad-center-policy-and-compliance.md).

## Evidence Standard

Each gate needs an attached command result, review record, or operational
artifact. A plan or a checkbox alone is not proof. The actual public switch and
each material funding acceptance are separate founder actions recorded with
their scope and terms.
