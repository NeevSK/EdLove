# Offline Authorization and Gating with Native WASM & Signed Snapshots

This document details the architectural decisions and implementation standards for offline-first authorization, local write safety gating, and dynamic policy execution on the Gurudevi Mobile client (React Native / Hermes).

---

## 1. Context & Background

The Sanctuary platform utilizes **Cedar Policy** for fine-grained authorization. In an offline-first mobile environment, authorization must occur locally on SQLite data to prevent UI glitches, secure user credentials, and defend against local write attacks while disconnected from the server.

Operating in a React Native / Hermes environment presents the following constraints:
1. **Hermes WASM Engine**: Hermes in React Native 0.84+ brings native WebAssembly support, enabling dynamic Cedar policy evaluation offline.
2. **Device Resource Constraints**: Compiling dynamic Cedar rules into WASM memory is heavy on CPU and battery, and old devices might lack WASM support entirely or fail to load wasm bundles.
3. **Replication Safety**: Offline mutations made locally on the database must be verified BEFORE they are queued in the replication streams (e.g. PowerSync transaction log), ensuring fail-secure data integrity.

---

## 2. Decision & Design

We implement a **Dual-Mode Local Policy Decision Point (PDP)** combined with a **Secure Drizzle Write Interception Wrapper**:

### A. Fallback Offline Policy Evaluator (`localEvaluator.native.ts`)
The native client checks permissions offline using a layered fall-secure mechanism:
1. **WASM Mode (First Attempt)**: The client queries local SQLite table `cedar_policies` for Cedar DSL rules. If present and within memory limits ($< 100\text{ KB}$), it dynamically loads `@cedar-policy/cedar-wasm/web` and executes raw Cedar dynamic checks against local SQLite entities.
2. **Snapshot Mode (Fallback)**: If WASM is unsupported, fails to load, or throws a compilation crash, it catches the error and falls back to a signed, cached permission snapshot map (`permission_snapshots` table) generated by the server. 
3. **HMAC SHA-256 Signature Guard**: The snapshot record's integrity is validated using strict key ordering (`generatedAt`, `expiresAt`, `userId`, `schoolId`, `permissions`, `temporalHints`) against an HMAC signature to prevent local root database database tampering.

```mermaid
graph TD
    A[Start local check] --> B{Local Cedar rules in SQLite?}
    B -- Yes --> C{WASM engine compiles?}
    B -- No --> F[Query signed snapshots table]
    C -- Yes --> D[WASM dynamic evaluation]
    C -- No --> F
    D --> E[Decision Allowed/Denied]
    F --> G{HMAC Signature & Lease Valid?}
    G -- Yes --> H[O(1) JSON Map Lookup]
    G -- No --> I[Fail Secure: Deny]
    H --> E
```

### B. Secure Drizzle Proxy Gating (`database.ts`)
To prevent client-side write errors from polluting background sync replication streams:
1. All local mutations (`insert`, `update`, `delete`) execute through a secure Drizzle client wrapper proxy (`createSecureDrizzleProxy`).
2. The proxy intercepts the mutation before database driver compilation.
3. It evaluates the operation against the local PDP evaluator (`checkLocalPermission`).
4. If denied, it aborts the operation and throws a structured `SovereignError` (code `LOCAL_WRITE_VIOLATION`), preventing SQLite write commitment and blocking transaction queuing for background replication.
5. If allowed, it executes the SQLite write, where PowerSync intercepts the statement and queues it for asynchronous bulk upload.

---

## 3. Implications

* **Fail-Secure Defaults**: Any validation errors or runtime crashes default to `false` (access denied).
* **Battery & Performance Efficiency**: Normal route checks and quick queries use snapshot caches to bypass heavy WASM compiling.
* **Security at rest**: If a rooted device modifies local tables or injects arbitrary policy strings, signature verification fails and locks access.
