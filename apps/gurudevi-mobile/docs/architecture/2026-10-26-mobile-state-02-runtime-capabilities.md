## Grounding and version authority

This is a 2026-10-26 capability assessment of the actual mobile installation, not a list of APIs remembered from an earlier React era. Package.json ranges, installed package manifests, concrete source/declaration files, RN Terrain affordance output and dated upstream releases were checked separately. No dependencies were added or upgraded.

The React baseline is **19.3.1**, React Native **0.88.0**, Expo **58.0.17**, Router **58.0.25**. RN Terrain radar:upstream reports React 19.3.1, Zustand 5.0.16, XState 5.33.3 and MMKV 4.3.2 as latest stable on this audit date; XState additionally has 6.0.0-alpha.70. “Latest” is a dated registry result, not a reason to adopt an alpha or change a native cohort. The installed baseline is already current for these four; topology and usage are the main problem.

## React: choose less state before choosing another state engine

| Affordance | Actual architectural use | Does not replace | Source-grounded application here |
| --- | --- | --- | --- |
| Render-time derivation | Compute values from existing facts; use memoization only for demonstrated expensive work | Persistence or an external authority | Challenge temporal phase/isPastView, version isBlocked, themeMode aliases and selected entity metadata before moving them anywhere. |
| useState / useReducer | Component, route or bounded subtree ownership; event-driven local transitions | Cross-runtime durable work | Drawer/overlay visibility, local command errors and one-form interaction do not earn a global store by default. |
| Context with direct provider syntax | Subtree-scoped dependency/configuration and lifecycle ownership | Fine-grained subscriptions for every consumer | Configurable mascot, portal roots and account-owned services can legitimately be tree-bound. Changing provider syntax is cosmetic unless ownership changes. |
| ref as ordinary prop | Simpler component APIs without a forwarding wrapper | Native host capabilities | Follow repository policy for new React 19 code; do not mechanically rewrite working components during this audit. |
| useSyncExternalStore | Observe an existing external owner with cleanup and stable snapshots | An automatic reason to create a new singleton store | Appropriate when an existing service already has events; do not hand-build a new state library when MMKV, Query or PowerSync already offers a hook. |
| useActionState | State/result/pending lifecycle for a component-owned Action | Durable queue, cross-account settlement, native HTML forms | Can remove manual local pending/result bookkeeping in a qualified native pilot; invoke native Actions explicitly, with renderer and mounted evidence. |
| useOptimistic | Temporary component projection while an Action is pending | Server confirmation, durable outbox, conflict policy | Candidate for immediate UI feedback over an existing confirmed owner, never for command recovery after process death. |
| useTransition / useDeferredValue | Distinguish urgent interaction from less urgent rendering | Worklet thread execution or making synchronous I/O free | Useful for expensive derived lists; not a cure for four whole-store subscriptions or blocking storage. |
| useEffectEvent | Read latest committed values inside effect-owned callbacks without resubscribing for unrelated values | Dependency correctness or ordinary press handlers | Review long-lived native subscriptions with ref-based callback mirrors; do not use it to silence missing dependencies. |
| Compiler | Build-time memoization of compatible React code | Correct ownership, query keys or native performance measurements | Babel preset has reactCompiler:true. Verify transformed coverage, including shared packages, before deleting purposeful memoization. |
| Suspense / error boundaries | Explicit loading/error composition for compatible resources | Durable storage or a state machine | Avoid a global waterfall that blocks all public routes for optional services. |
| Activity | Renderer-level hidden subtree behavior and lifecycle semantics | Free retention or a low-memory eviction policy | The installed Fabric renderer contains Activity handling; do not retain every tab on 2 GB hardware without a measured memory/lifecycle pilot. |

React's [effect guidance](https://react.dev/learn/you-might-not-need-an-effect) supports deriving display data directly and handling actions in event paths; redundant synchronization creates extra work. [External-store contracts](https://react.dev/reference/react/useSyncExternalStore) require stable immutable snapshots and subscription cleanup. Those are architecture rules, not a mandate for more stores.

[useActionState](https://react.dev/reference/react/useActionState) supplies an Action result and pending state. [useOptimistic](https://react.dev/reference/react/useOptimistic) supplies a temporary Action-scoped view. [useEffectEvent](https://react.dev/reference/react/useEffectEvent) is restricted to effect-owned logic. None establishes disk durability or replay safety. The [Compiler](https://react.dev/learn/react-compiler/introduction) can reduce manual memoization but cannot choose the correct owner.

Physical proof: react/cjs/react.development.js exports useActionState, useOptimistic, useEffectEvent, Activity and ViewTransition; @types/react/index.d.ts declares the hooks. ReactFabric-dev.js contains native Action/optimistic/effect-event implementations and Activity paths. Export presence and renderer code are stronger than memory, but not a substitute for mounting the chosen API in the target build. Hook declarations can outpace a particular renderer or build configuration.

### React 19.3 is not a blanket native capability grant

The [September 9 React 19.3 release](https://react.dev/blog/2026/09/09/react-19-3) introduces stable ViewTransition/Fragment Refs, DOM browser()/Trusted Types and Server Component context improvements. It explicitly describes ViewTransition as DOM-only at release. Do not turn those announcements into a native animation rewrite. React core exports, renderer implementation, channel, platform host support and physical proof are separate gates. The .1 patch number also does not make every earlier React primitive newly introduced in 19.3.

## React Native 0.88: relevant baseline and limits

The [October 19 RN 0.88 release](https://reactnative.dev/blog/2026/10/19/react-native-0.88) changes event dispatch to the web-based path by default, adds variable fonts and iOS SceneDelegate support, and documents ArrayBuffer TurboModule and experimental SwiftPM work. It identifies imperative addEventListener APIs on native refs as Canary in 0.88. Stable event props remain the app-facing baseline; do not copy Canary examples into this stable installation merely because the version number matches.

Fabric, TurboModules and JSI reduce particular communication costs; none implies zero latency, a shared arbitrary JS object graph across worklet runtimes, or free synchronous storage. Expensive JS, JSON serialization, repeated subscription work, native module construction, layout and GPU work still consume time. RN does not provide account isolation, idempotent network commands or an app-wide persistence authority automatically.

Native AppState, color scheme, dimensions, accessibility and network modules already produce observations. Store only app-owned overrides or a necessary validated snapshot; avoid independently persisting a copy of every system observation. The installed declarations still expose some legacy symbols (including findNodeHandle); presence does not override the repository's stricter dialect veto.

## Zustand 5.0.16: use its real subscriptions, not a facade imitation

Installed index.d.ts re-exports vanilla and react. react.d.ts declares selector-aware useStore and create; vanilla.d.ts provides createStore and getState/setState/subscribe. react/shallow.d.ts and middleware/subscribeWithSelector.d.ts exist. Middleware persist.d.ts already supplies partialize, version, migrate, merge, skipHydration, rehydrate, hasHydrated and hydration listeners. [The exact upstream release](https://github.com/pmndrs/zustand/releases/tag/v5.0.16) was checked; unavailable generic migration URLs were not treated as evidence.

These affordances allow a retained store to have a deliberate instance lifetime, narrow subscriptions and explicit restoration without inventing another global hydration framework. A small shared in-memory model can be justified; persisted booleans do not automatically require one. Composite selector results must remain stable or use an appropriate equality/shallow convention; migrating from the facade to fresh object-returning selectors without checking stability can introduce another problem. getState is an imperative snapshot, not a reactive subscription. subscribeWithSelector is middleware, not magic on every store.

Current named static Zustand imports in the scanned production TS/TSX estate use create/createJSONStorage/persist and types; no direct useShallow, createStore, subscribeWithSelector or skipHydration usage was found in the mobile/core/UI search. This is an opportunity list, not a requirement to use all of them.

## MMKV 4.3.2: persistence can already be reactive

RN Terrain grounded **11 exports**, including useMMKVString, useMMKVBoolean, useMMKVNumber, useMMKVObject, useMMKVListener and useMMKVKeys, plus createMMKV/existsMMKV/deleteMMKV. The [hook documentation](https://github.com/mrousavy/react-native-mmkv/blob/main/docs/HOOKS.md) and [4.3.2 release](https://github.com/margelo/react-native-mmkv/releases/tag/v4.3.2) were checked against installed lib/hooks and lib/specs declarations.

A simple native preference may need only its keyed value, a validated default and a dependency-provided reactive hook. That can avoid copying the value into Zustand and persisting it back again. The installed string hook accepts an optional explicit instance and returns a value/setter pair; the object hook uses JSON serialization. No such hook calls were found in mobile/core/UI production sources.

This is conditional simplification, not an instruction to import MMKV into platform-neutral core. The active StorageManager port has no key-change subscription and main bootstrap defaults to AsyncStorage for documented startup concerns. Use one correctly scoped app-owned/native adapter instance; a hook using MMKV's default instance would not observe the existing gurudevi-store namespace. Establish enabled backend, instance identity, hydration, encryption/key custody if applicable, corruption behavior and read-old/write-new migration before adoption. Synchronous writes and object serialization can block JS; prefer bounded low-frequency preference payloads.

The installed MMKV.nitro.d.ts says byteSize is a number, set returns void, getString returns string|undefined, and recrypt exists. The local mmkv-guidance skill instead describes byteSize/return values differently and forbids recrypt as absent. This is a concrete stale-guidance conflict: do not emit APIs from that skill without physical verification, and do not treat this report as approval to change encryption or use a forbidden API. Reconcile the policy separately. The native/storage.ts byteSize wrapper currently assumes a different shape; inspect actual consumers before claiming impact.

## XState 5.33.3: admitted protocol tool, not installed architectural obligation

The installed dist/declarations/src/index.d.ts exports setup, createMachine, createActor, transition/initialTransition, actor creators and helpers. [The exact 5.33.3 release](https://github.com/statelyai/xstate/releases/tag/xstate@5.33.3) was inspected. Current general Stately pages may show v6 alpha; they cannot define this app's v5 API. No production import was found in the audited TS/TSX scope, and @xstate/react is not a declared mobile dependency.

Use an actor only if it replaces an existing, demonstrably awkward legal-transition/cancellation/recovery protocol. It must have an owner, lifetime, typed events, side-effect boundary, stop/cancel behavior and explicit persistence policy. A pure reducer remains a legitimate smaller answer. Making a machine and retaining the old independently writable stores makes the estate larger.

The [persistence reference](https://stately.ai/docs/persistence) distinguishes getPersistedSnapshot from a live snapshot and warns about restoration semantics and compatibility; current-page channel must be verified against v5. Stored workflow state does not itself give exactly-once remote effects. Receipt/idempotency contracts remain necessary. Do not adopt the v6 preview to satisfy a “modern” label.

## Query 5.104.5 and PowerSync: data already has owners

| Dependency | Physically grounded capability | Existing use | Architectural consequence |
| --- | --- | --- | --- |
| @tanstack/react-query 5.104.5 | query/mutation hooks, cache observers, useMutationState, queryOptions, scope-aware cache methods via QueryClient | Principal-scoped notification/security hooks and many domain reads | Remove a duplicated remote read model only after freshness, cancellation, scope and failure semantics are preserved. |
| @powersync/react 2.0.2 | useQuery, useStatus, stream and suspense query hooks | adapters/powersync/hooks.ts and PowerSync contexts | A reactive SQLite-backed read need not be mirrored into a Zustand entity map or second Query cache. |
| @powersync/react-native 2.3.1 / drizzle-driver 0.8.0 | Database lifecycle and compiled Drizzle query integration | Account-scoped runtime/provider and domain hooks | Opening/closing an account database and durable writes remain lifecycle responsibilities, not display state. |
| @tanstack/react-pacer 0.22.1 | Existing debounce/throttle hooks | App usePacer wrappers | Consider for a real scheduling need; do not replace a durable command retry journal with a UI debounce helper. |

The [Query v5 native guide](https://tanstack.com/query/v5/docs/react/react-native) describes explicit onlineManager/focusManager wiring for reconnect and AppState. No named wiring was found in the mobile/core/UI source search. Establish whether another runtime adapter already supplies it, then prove background/resume and reconnect behavior; the absence is a review lead, not a claim that Query is broken. Current app query defaults specify retries and staleTime but not those lifecycle integrations.

Query select is an observer projection, not a second entity owner. Query error/pending state can often eliminate separate read-status booleans. A Query cache does not survive restart by default; persisting private results needs its own allowlist, scope and expiry policy. PowerSync local reads have different authority and durability from ephemeral remote caches. Document the actual resource path before assigning either tool.

## Gestures, animation, audio and native UI

Reanimated 4.7.1 and Worklets 0.13.0 already expose shared/derived values and animation/gesture-driven execution. Keep per-frame positions/intensity in the appropriate animation owner where justified, not global React state. Worklets threads.d.ts declares scheduleOnRN and scheduleOnUI. [The 0.13 scheduling reference](https://docs.swmansion.com/react-native-worklets/docs/threading/scheduleOnRN/) specifies an explicit hop to execute an RN-runtime function from a worklet; an ordinary sensory singleton is not intrinsically worklet-safe. Exports can retain deprecated compatibility helpers; follow the stricter repository import rules.

RNGH 3.4.0 supplies Gesture/GestureDetector through re-export paths; Terrain's abbreviated output omitted GestureDetector even though the app imports it. Expo Router 58.0.25's Terrain output similarly missed most route exports. Follow the actual declaration re-exports. A scanner list is neither an exhaustive symbol oracle nor a semantic classifier: its “components” list included TypeScript interfaces and deprecated APIs.

Installed expo-audio 58.0.10 supports component-owned hooks and imperative players; [SDK 58 audio documentation](https://docs.expo.dev/versions/v58.0.0/sdk/audio/) is the version-matched reference. Choose lifetime deliberately and release native resources. A player hook can be the simplest correct owner; a singleton is not automatically faster. Installed @expo/ui 58.0.22 has no named static TS/TSX imports in this scan. It is a future native-control candidate, not evidence that replacing every existing primitive would improve this state seam. FlashList and LegendList are already used in different shared consumers; choose by measured list behavior, not by installing a third list engine.

## External alternatives: admission, not shopping

No new dependency is currently justified by this audit. Jotai/Nanostores/signals would add another ownership system without addressing the proven facade or mirrored scope. @xstate/react would only be considered after a specific v5 actor pilot needs React integration; the installed core alone is not a reason to add it. A storage subscription adapter is only justified if a retained platform-neutral requirement cannot be served by an existing native-owned path. Any candidate must show a concrete requirement the installed stack cannot meet, exact version/channel/native support, code it would replace, failure/lifecycle evidence, and net maintenance cost.
