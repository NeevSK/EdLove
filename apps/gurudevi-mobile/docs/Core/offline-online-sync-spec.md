# Offline-Online Synchronization Spec

This document defines the synchronization logic, conflict resolution rules, and offline data handling boundaries for Gurudevi.

---

## 1. Local-First Mutation Flow (The Sync Queue)

To survive rural Sri Lankan network disruptions, all database mutations must execute locally first before replicating to the cloud.

1. **Optimistic Write**: UI triggers a write -> immediately applied to the local SQLite database via Drizzle/OP-SQLite, updating the screen instantly.
2. **Queue Insertion**: The write mutation is appended to the local PowerSync sync queue table.
3. **Background Replication**: When connectivity is detected, the PowerSync engine processes the queue sequentially, forwarding payloads to the Hono API gateway.
4. **Reconciliation**: Once the API returns a successful write confirmation, the queue item is purged, and the local SQLite record is updated with server-reconciled fields.

---

## 2. Idempotency Strategy

Under patchy 3G/LTE signals, native clients often retry network requests. To prevent duplicated records (especially on high-volume lists like attendance or marks), we enforce **Strict Idempotency**:

* **Client Transaction Keys**: Every mutation payload generated by `@repo/core` stores must include an `idempotency_key` (UUID format).
* **Gateway Check**: The Hono API gateway verifies this key before persisting writes. If a transaction with the same key has already succeeded, the server discards the duplicate write but returns a `200 OK` using the cached response payload.

---

## 3. Soft Deletions Policy

Physical record deletes (`DELETE FROM`) are prohibited on client SQLite databases to prevent orphan relations and database corruption during synchronizations.

* **Deletion Flag**: Deleting an item marks a `deleted_at` timestamp or sets `is_deleted = true`.
* **SQLite Scope**: Local queries filter out records where `is_deleted` is true.
* **Purge Cycle**: Physical database cleanup is handled exclusively on the remote Postgres database, and sync projections automatically sync these deletions downward to clean local SQLite storage.

---

## 4. Conflict Resolution (Last-Write-Wins)

When multiple devices write to the same record (e.g., two teachers editing a shared lesson plan collection), conflicts are resolved using a **Temporal Last-Write-Wins (LWW)** strategy:

* **Event Timestamp (`occurred_at`)**: Resolution is based on the client-side `occurred_at` timestamp (the actual event time), not the `created_at` timestamp (the server upload time).
* **Drift Control**: Clients synchronize device time with the gateway server during session bootstrap to prevent local time drift from corrupting conflict decisions.
