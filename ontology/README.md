# Gurudevi ontology

`gurudevi.yaml` is the one hand-written source for what exists in Gurudevi and how each
thing comes to be and changes. The decision behind it, and the order of work, is
[docs/decisions/2026-11-26-gurudevi-tool-selection.md](../docs/decisions/2026-11-26-gurudevi-tool-selection.md).
The research and evidence are indexed in
[docs/architecture/2026-11-26-api-foundation/README.md](../docs/architecture/2026-11-26-api-foundation/README.md).

This folder is **build step 1**: the ontology file with the shared case, examples that
pin its behaviour, and the pinned tools in CI. Nothing here touches the running API yet.

## What is in it

| Path | What it is | Written or generated |
| --- | --- | --- |

| `examples/valid/<Class>.yaml` | Objects that must pass. Also the context the cross-object rules are checked against | Written |
| `examples/invalid/<defect>.yaml` | One planted defect each (the seven from the shared case, plus two) | Written |
| `examples/expected.yaml` | Which check must catch each defect | Written |

| `scripts/check-reality.py` | Refuses a class that takes no reality form, or breaks its form's requirements | Written |
| `links/links.yaml` | The joins no tool can read off the code: table per class, column per slot, ontology change per API capability, where the code spells each enum | Written |

The shared case: **Person**, **Institution**, **Bond**, **Enrollment** (a Bond in the student
capacity) and **Authority** (a power a bond grants), from

## Run it

```sh
eval "$(ontology/tools/install.sh | grep '^export')"   # once; tools go to .ontology-tools/
ontology/check.sh
```

`install.sh` needs Python 3.13, Java 17+, Node and npm. CI runs the same two commands in
[`.github/workflows/ontology.yml`](../.github/workflows/ontology.yml) on any change under
`ontology/`.

Today `check.sh` runs `linkml lint` (zero warnings allowed) and the examples. It prints the
rule ids whose checks are still waiting for the generator:

```
ok: 5 valid files pass; 9 invalid examples behave as expected
   waiting for generated rule checks: authority-within-bond, capacity-decides-powers, interval-order, one-active-bond
```

For a rule-caught example, the check asserts that LinkML alone still **passes** it. That
proves the rule is needed, and it fails the day someone moves the fact into native LinkML
without updating `expected.yaml`.

## Links: one chain from reality to the screen

Every layer is joined to the next, and a break anywhere is named. The chain:

reality level → reality form → ontology class → slot / enum / transition → zmodel model →
field / table → API capability (catalog.ts) → handler file and the tables it reads or
writes (router.ts, SQL, Postgres functions in migrations) → module → card → Cedar resource →
policy file → authorization subject → screen feature. Landscape subdomains join models and
modules from the side.

Only the joins no tool can see are written by hand, once, in `links/links.yaml`. The rest is
read from the files themselves, so it cannot drift. The API's own capability conformance
(`apps/sanctuary-api/scripts/capability-conformance.ts`) stays the owner of contract,
handler, evidence and client links; `links.py build --conformance` folds its report in
rather than repeating it.

Gaps have fixed codes (`LINK_BROKEN`, `SLOT_DIFFERS`, `VALUES_DIFFER`, `VALUE_SPELLINGS`,
`TRANSITION_NOT_BUILT`, `CAPABILITY_DIFFERS`, `CAPABILITY_TOUCHES_UNMODELLED`,
`TABLE_NO_CLASS`, `FEATURE_NO_CAPABILITY` and others; see `links.py`). Known gaps are
counted in `tooling/ratchet.json` (`ontologyLinkGaps`), the same ratchet the rest of the repo
uses: a count may only go down, and `LINK_BROKEN` is always 0. So a new deviation (say a
table starts holding a status value the ontology lacks) fails the check, and fixing one lets
the ceiling drop with `links.py update`.

How a change shows itself:

- `check.sh` rebuilds the graph and fails if `links/out` is stale, so every change to the
  chain appears in the PR diff.
- The Ontology workflow runs on every path the graph reads (schema, API, migrations,
  policies, registries, cards), and on a pull request writes the ripple against the base
  branch (nodes and links added or removed, gaps opened or closed, everything downstream)
  to the job summary.
- `python -I ontology/scripts/links.py impact slot:Bond.state` shows what a node must stay
  true to (upstream) and everything it reaches (downstream), with the open gaps on the way.

## Reality forms: the layer above

The model of reality (levels L0 to L7, in the doc "Gurudevi's model of reality") says what
kinds of thing exist before anything is educational. `reality/reality.yaml` holds its forms,
and each form lists the checks a class must pass to take it. For example, a Coupling needs two
parties, a lifecycle, and an ending that keeps history; a Course never changes once over; a
Norm can be withdrawn and is tied to its source.

`gurudevi.yaml` imports `reality/reality.yaml`, and each class takes one form as a mixin:
Person and Institution are Holons, Bond (and so Enrollment) is a Coupling, Authority is a Norm.
`Bitemporal` now lives in `reality.yaml`. `check-reality.py` runs in `check.sh` and fails CI
on any finding.

Wiring it first found 4 gaps, now closed (Neev approved, 27 Nov 2026): Person and Institution
had no lifecycle and no recorded time. Each now has `Bitemporal`, a `state` (`HolonState`:
active, ended) and a lifecycle (`person.register`, `person.close`, `institution.register`,
`institution.close`) whose end keeps history. Adding the `Bond` table's real `archived`
state to the Bond lifecycle is refused for Bond and, by inheritance, for Enrollment
(`ending_keeps_history`).

## How the file is written

### Where each kind of fact goes

- **One slot** (range, required, minimum and maximum, a fixed value): native LinkML on the
  slot or in `slot_usage`. Example: `grade` is 1 to 13; an Enrollment's `capacity` equals
  `student`.
- **An if-then inside one object**: native LinkML `rules:` on the class. Example: an ended
  bond must have `valid_to`.
- **Across objects, or comparing times**: the schema-level `rules` annotation. Example: an
  authority never outlives its bond.

Native facts are checked by `linkml-validate` today. The rules section will be emitted to
Alloy, CUE, Zod and SQL checks by the generator (steps 3 and 4).

### Lifecycle (ontogeny)

Each class that changes over time carries a `lifecycle` annotation. Structured values go
under `value:`, because LinkML 1.12.1 refuses nested annotation maps without it (this
replaces the YAML-in-a-string form of the Level 0 prototype).

| Key | Meaning |
| --- | --- |
| `state` | The enum slot that holds the state |
| `within` | Where permissions are checked: a slot, or a dotted path such as `granted_by.institution` |
| `start` | The state a new one starts in |
| `create` | The capability that brings a new one into `start` (`id`, `who`, `needs`, `why`) |
| `transitions[]` | `id` (capability id), `from`, `to`, `who`, optional `needs` and `ends`, `why` |

`who` holds `person` (the bond's own person), `system` (Gurudevi itself), or a capacity
held in an active bond with `within`. `needs` names a `Power` the actor must hold. `ends`
lists objects that end at the same valid time, which is how "an authority never outlives
its bond" is kept by the lifecycle (the Alloy fix). One capability id may appear on more
than one transition when the same act starts from different states (`bond.end`).

### Rules section

Each rule has `id`, `says` (plain words), `kind`, `class`, and the fields its kind needs.
The kinds are listed at the top of the section in `gurudevi.yaml`. The generator must
refuse an unknown kind.

### Words

Only Neev's words and the existing code's (decision rule 6). English labels are the class
and enum names. Sinhala and Tamil labels will go in as LinkML `structured_aliases` with
`in_language: si` / `ta` when Neev supplies them. None are guessed here.

## Choices made in this step

These were not spelled out in the docs. Each is easy to change.

1. **Native LinkML first, rules section only for what LinkML cannot say.** So `linkml-validate`
   catches five of the seven planted defects today. The generator will read both.
2. **States follow the shared case** (invited, active, suspended, ended), not the Level 0
   prototype (invited, active, ended, kept). With valid and recorded time on every bond,
   "kept" looked like history rather than a state.
3. **Capacities follow the shared case** (student, teacher, principal, guardian, founder),
   not the ten in the Level 0 prototype. The redesign is top-down, so today's code lists
   were not copied in.
4. **A creation capability per lifecycle** (`bond.invite`, `authority.grant`). The prototype
   had only transitions between states, so nothing said who brings a bond into being.
5. **`needs` links acts to powers.** `bond.invite` needs `invite`. The grants table
   (`capacity-decides-powers`) is the one from the CUE and SHACL runs.
6. **Authority has a small lifecycle** (held, ended) and ends with its bond (`bond.end`
   `ends` it). It is typed `ufo: mode`, as the tool-selection table lists.
7. **The `why` lines are drafts** in plain words. Neev owns them.

## Open questions for Neev

1. **Enrollment lifecycle.** The decision uses `enrollment.approve` as its example id, but no
   doc defines it. For now an Enrollment follows the Bond lifecycle unchanged
   (`bond.accept` and so on), and the `enrol` power is used by nothing yet. Should a
   principal approve an enrollment (`enrollment.approve`, needs `enrol`), and who starts it?
2. **Suspension.** Does a suspended bond keep its authorities (today: yes), or do they end
   and come back on restore?
3. **"kept".** Is it a state of its own, or is it covered by valid and recorded time?
4. **Sinhala and Tamil words** for Bond, capacity, Authority and Enrollment (already open in
   the decision).
